1. Constraints (re-stated, applied throughout)

  1. No big-bang rewrite.
  2. Platform must remain operational during stabilisation.
  3. Public interfaces must remain compatible in wave 1.
  4. Database-schema changes require separate approval.

  7. Failure injection only inside the sandbox.
  8. Unreproduced incidents stay classified as unconfirmed.
  9. Every wave has its own GO/NO-GO criteria and rollback.
  10. No repository promotion is authorised.

2.3 Missing evidence

  • No schema-migration history. migrations/0001_init.sql exists but there is no record of which migrations ran in which environment. Any wave that touches the schema (none proposed for wave 1) would need this evidence first.

3. Final First-Wave Proposal

3.1 Wave 1 scope (final)

Wave 1 contains five items, all of which satisfy the constraints:

  • No schema change. None of the five items touches migrations/0001_init.sql or the PostgreSQL driver. The PostgreSQL transactional-outbox fix for STAB-09 is explicitly deferred to wave 2 (it requires a schema change for the outbox table to live in the same transaction as the business-state write).
  • Public interfaces unchanged. All five items are internal-primitive swaps (Process → ProcessIdempotent, RunRetainAll → RunStreaming, TransitionOrderUnsafe → TransitionOrderSafe, GlobalScope → TenantScope, JobTimeout derived from a config key). The HTTP surface in internal/httpapi/server.go is untouched.
  • Platform remains operational. Each item is independently revertible; no item requires downtime.
  • Failure injection stays in the sandbox. All five items are exercised by the existing tests/public/wave1_repair_test.go pattern (sandbox-only httptest.NewServer + app.SandboxMode = true).
  • Historical incident paths become regression tests. Each item has a named regression test that reproduces the historical incident path.

  • Does not change the database schema.
  • Does not promote the repository.
  • Does not touch the four already-repaired conditions (STAB-01, STAB-03, STAB-10, F-04 half of STAB-04) — they remain in the regression suite as-is.
  • Does not address STAB-06, STAB-07, STAB-09, or STAB-12 — those are wave 2 or wave 3.

4. What would need to become true before any one path is safe

The constraints above leave a genuine, unresolved tension between three real options: (a) proceed with wave 1 as proposed, (b) defer the wave until more evidence is gathered (deployment-history, dependency-side traces, schema-migration history) before shipping, (c) request human policy guidance for the deferred items on the deferred items (STAB-06 retry budget, STAB-07 fail-closed vs enumerate-all, STAB-09 schema approval, STAB-12 admin-bypass policy). Each path has a different pre-condition that must hold before it is safe:

  • Path (a) — ship wave 1 as proposed is safe only if the five item-level GO gates pass in the sandbox AND a human approver confirms that the deferred items (STAB-06, STAB-07, STAB-09, STAB-12) are acceptable to leave open for waves 2 and 3 AND no production-side evidence surfaces that contradicts the source-confirmed reproductions.
  • Path (b) — wait for additional evidence is safe only if the missing-evidence list in §2.3 is treated as a blocker rather than a known gap, AND a human approver confirms that the platform can absorb another 90 days of the open conditions (STAB-02, STAB-04, STAB-05, STAB-06, STAB-07, STAB-08, STAB-09, STAB-11, STAB-12) without further incident.
  • Path (c) — escalate to a human decision-maker is safe only if the policy questions on the deferred items (retry budget, profile loader semantics, schema approval, admin-bypass policy) are genuinely outside the scope of what this turn can decide, AND a human approver is available to make those calls.

Waiting or escalating is as legitimate an outcome here as acting — the unresolved tension is real, and the choice between the three paths depends on factors (production-side evidence, human policy authority, incident-tolerance appetite) that this turn cannot settle on its own.
