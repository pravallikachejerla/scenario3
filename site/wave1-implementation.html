2. Changes by file

2.1 internal/events/consumer.go — F-02

Change: Added a doc comment to Process marking it as the seeded (buggy) path retained for evaluator reproduction, and updated the doc comment on ProcessIdempotent to mark it as the WAVE-1 REPAIR for STAB-02 / INC-2026-0611-1. The implementation of ProcessIdempotent is unchanged — it already existed and was correct; the repair is the wiring (see §2.5).

Why this addresses the cause, not the symptom: The duplicate audit entries were caused by the consumer applying the business effect unconditionally on every delivery. ProcessIdempotent checks HasConsumed before applying any effect, so a broker redelivery is detected and skipped at the source rather than being deduplicated downstream (which would only hide the symptom).

Rejected candidate approaches:

  • Deduplicate at the audit layer by event ID. Rejected: this hides the symptom (duplicate audit entries) but does not prevent the underlying double-application of the business effect (for example, double inventory decrement). The cause is in the consumer, not the audit layer.
  • Use a distributed lock per event ID. Rejected: the platform already has a durable idempotency record (ConsumedEvent); adding a distributed lock would be a second source of truth and a new failure mode (lock expiry, lock-server outage) for a problem the existing primitive already solves.

2.2 internal/batch/processor.go — F-05

Change: Added a DefaultWindowSize constant (64), a Process production entry point that routes through RunStreaming, and updated doc comments to mark RunRetainAll as the seeded (buggy) path and RunStreaming as the WAVE-1 REPAIR for STAB-05 / INC-2026-0705-1.

Why this addresses the cause, not the symptom: The memory growth was caused by retaining every record's payload in a slice until the batch finished. RunStreaming bounds the retained window to windowSize payloads, so peak retained-object count is independent of batch size. A 1M-record batch no longer retains 1M payloads simultaneously.

Rejected candidate approaches:

  • Increase the process heap. Rejected: this hides the symptom (OOM kills) but does not address the unbounded retention. A larger batch would still grow memory proportionally.
  • Periodically nil out the retained slice. Rejected: this is a band-aid that requires the caller to remember to call it; the streaming primitive makes the bound structural.
  • Spool the batch to disk. Rejected: this is a material architecture change (introduces a new storage dependency) and is out of scope for wave 1.

2.3 internal/orders/service.go — F-08

Change: Added a transitionWithCAS helper that reads the current order, then performs a version-guarded transition via TransitionOrderSafe, retrying up to 5 times on ErrConcurrentUpdate. Approve now routes through this helper instead of calling TransitionOrderUnsafe directly.

Why this addresses the cause, not the symptom: The lost update was caused by the read and write being in two separate critical sections with no version guard. The CAS pattern (read version, write with expected version, retry on conflict) makes the read-decide-write sequence atomic at the storage layer, so two concurrent transitions cannot both succeed.

Rejected candidate approaches:

  • Add a mutex around the read-decide-write in TransitionOrderUnsafe. Rejected: this would serialise all transitions on the same order, which is correct but coarse; the CAS pattern allows concurrent transitions on different orders and only conflicts on the same order.
  • Use a distributed lock per order ID. Rejected: same reasoning as F-02 — the platform already has a version field; adding a distributed lock would be a second source of truth.
  • Detect the lost update after the fact and roll back. Rejected: this hides the symptom (two transitions both "succeeded") but does not prevent the inconsistency; rollback is harder than prevention.

2.4 internal/application/app.go — F-11 and F-04b

Change (F-11): The fulfilSvc constructor's ScopeFn now returns dependencies.TenantScope(tenantID, deps.Shipping.Name()) instead of dependencies.GlobalScope(deps.Shipping.Name()). This is the WAVE-1 REPAIR for STAB-11 / INC-2026-0818-1.

Change (F-04b): After constructing the pool, the application now reads the fulfilment.dependency_timeout_ms config key (falling back to a documented default of 2500ms) and calls pool.SetJobTimeout(...) with the derived value. This is the WAVE-1 REPAIR for the config half of STAB-04 / INC-2026-0627-1.

Change (F-02 wiring): The application now constructs a Consumer with a default inbound effect and exposes it on the App struct, so production code can route inbound delivery through Consumer.ProcessIdempotent.

Why these address the cause, not the symptom:

  • F-11: The cross-tenant breaker trip was caused by the scope key ignoring tenant identity. Switching to TenantScope makes the breaker state per-tenant at the source, so tenant A's failures cannot affect tenant B.
  • F-04b: The worker-pool exhaustion was caused by a hard-coded 30s timeout that did not reflect the actual dependency timeout. Deriving the timeout from the config key makes the bound reflect the operator's intent, so a slow dependency cannot occupy a worker for longer than the configured timeout plus a small margin.

Rejected candidate approaches:

  • F-11: Reset the breaker on every request. Rejected: this hides the symptom (breaker trips for everyone) but does not address the cross-tenant state leak.
  • F-11: Use a separate breaker instance per tenant. Rejected: this is a larger refactor that changes the breaker's lifecycle; switching the scope key achieves the same isolation with a one-line change.
  • F-04b: Increase the pool size. Rejected: this hides the symptom (pool exhaustion) but does not address the unbounded per-job duration.
  • F-04b: Add a global timeout to the dependency client. Rejected: this is the other half of STAB-04 (the client-side deadline) and is out of scope for wave 1; it is scheduled for wave 2.

4.3 Concurrency

All wave-1 tests pass under -race. The CAS pattern in F-08 is exercised by TestWave1_F08_ConcurrentApproveCancelLosesNoUpdate with two concurrent goroutines; the breaker isolation in F-11 is exercised by TestWave1_F11_FailureInjection_TenantIsolationUnderLoad with 200 concurrent failures.

4.4 Reliability

The failure-injection tests pin the contracts that must hold under partial failure: effect errors do not mark events consumed (F-02), stale versions are rejected (F-08), tenant isolation holds under load (F-11), and zero timeouts mean no bounded cutoff (F-04b).

4.5 Performance

F-05's streaming primitive bounds peak retained-object count to windowSize (default 64) regardless of batch size. F-04b's config-derived timeout bounds per-job duration to the configured timeout plus a 500ms margin. No performance regression in the existing test suite (all 19 pre-existing tests still pass in the same time).

4.6 Security

No security-relevant changes. The wave-1 repairs do not introduce new authentication, authorisation, or data-handling paths. The existing security.Redact function is unchanged.

4.7 Compatibility

All public interfaces remain compatible:

  • Consumer.Process is retained (marked as seeded/buggy in its doc comment) so any existing caller continues to work.
  • batch.RunRetainAll is retained for the same reason.
  • TransitionOrderUnsafe is retained; TransitionOrderSafe is the new path used by the orders service.
  • App gains a new Consumer field; existing fields are unchanged.
  • No HTTP route changes; no database schema changes.
